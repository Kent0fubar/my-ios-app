# MacなしでiOSアプリを作った話 — AIに投げたプロンプトと、返ってきた結果を全部見せます

新人エンジニアの僕が、AIコーディングアシスタント「Antigravity」に6つのプロンプトを投げたら、7時間後にセキュリティテストまで通ったiOSアプリが出来上がっていた。

業務でWebの保守・開発はやっているけど、モバイルアプリは完全に未経験。そんな自分でもここまでできた、という話。

---

## なぜこの記事を書いたのか

この記事は、新人エンジニアの自分が、AIコーディングアシスタントに指示を出しながら、WindowsだけでiOSアプリを作った7時間の全記録です。投げたプロンプトも、返ってきたコードも、失敗した過程も載せます。

生成されたコードの全容を把握し、何をしているのか理解してから採用した。新人だからこそ、ブラックボックスにしたくなかった。分からない部分はAIに「この処理は何をしているのか説明して」と聞きながら進めた。結果的に、この進め方が一番の勉強になった。

---

## この記事の読み方

自分がAIに投げた指示（プロンプト）を 💬 で、AIが返した結果を 🤖 で表記しています。

同じプロンプトを投げれば、同じような結果が得られるはずです。再現性を重視して書きました。

## Step 1：「環境作って」と言っただけで20ファイル生成された

### 💬 プロンプト①

> iOSアプリの開発環境をセットアップしたい。Windows環境です。

たったこれだけ。

### 🤖 AIがやったこと

AIはまず「WindowsではXcodeが使えない」という制約を理解した上で、代替手段を提案してきた：

- React Native (Expo) — JavaScriptベースなのでWindowsでも開発可能
- EAS Build — クラウド上でiOSビルドできる（Macいらない）
- Expo Go — スマホにアプリを入れるだけで実機テスト可能

そしてそのまま、プロジェクトの作成から依存パッケージのインストールまで全部やってくれた。生成されたのは20以上のファイル。画面、認証、データベース接続、位置情報サービス、メディア処理、プッシュ通知…。

一つのプロンプトで、アプリの骨格が丸ごとできた。

正直、この時点で「もう半分できてるじゃん」と思った。ただし、ここから先が本番だった。

---

## Step 2：「セキュリティ確保して」で3つの脆弱性が見つかった

### 💬 プロンプト②

> Secure Supabase Backend — Supabaseバックエンドのセキュリティを確保してください。RLSポリシーの実装、認証と認可のチェック強化、不正なデータ変更の防止をお願いします。

### 🤖 AIがやったこと

AIは6つのモジュールを順番に読み込んで、セキュリティ監査を実施した。テーブル定義、データアクセス層、認証処理、ファイルアップロード、セッション管理、画面遷移ガード。

そして3つの脆弱性を発見した。

脆弱性1：ユーザーが自分でプレミアム会員になれる

プロフィール更新のポリシーが「本人なら何でも変更OK」になっていた。つまり、APIを直接叩けば「is_premium: true」に書き換えられてしまう。

修正として、データベースのトリガーでプレミアムフラグの変更を自動的に無効化するコードが生成された：

```sql
-- ユーザーが特権フィールドを変更しようとしても、元の値に戻す
CREATE OR REPLACE FUNCTION protect_privileged_fields()
RETURNS TRIGGER AS $$
BEGIN
    IF OLD.is_premium IS DISTINCT FROM NEW.is_premium THEN
        NEW.is_premium := OLD.is_premium;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

脆弱性2：他人のアバターを上書きできる

ファイルアップロード処理で、IDのチェックがなかった。つまり、他人のIDを指定すれば、他人のプロフィール画像を差し替えられる。

脆弱性3：ログインしなくても画面が見える

URLを直接入力すると、認証を通さずにアプリの中身が表示されてしまう。

211行のセキュリティパッチSQLが自動生成された。自分でSQLを1行も書いていない。

## Step 3：AIが書いたコードにAIが脆弱性を見つけた

ここが一番面白かった部分。

### 💬 プロンプト③

> SQLインジェクション対策がされているか確認をしてください。

### 🤖 AIが見つけたもの

AIがデータアクセス層を精査した結果、3箇所の危険なコードを発見した。

```typescript
// ❌ AIが最初に書いたコード：IDに悪意のある値が入ると危険
.or(`user1_id.eq.${userId},user2_id.eq.${userId}`)
```

テンプレートリテラルでフィルター文字列を組み立てている箇所は、PostgRESTフィルター注入という攻撃が成立する。

修正として、全てのIDにUUID形式の検証が追加された：

```typescript
const UUID_REGEX = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;

function validateUUID(id, fieldName = 'ID') {
    if (!UUID_REGEX.test(id)) {
        throw new Error(`無効な${fieldName}形式です`);
    }
}
```

UUID以外の文字列は、クエリに到達する前に全部弾く。シンプルだけど確実な対策。

この経験で学んだこと：AIは「動くコード」を書くのは得意だが、「攻撃されたらどうなるか」という視点は弱い。セキュリティの最終判断は人間がやる必要がある。

新人の自分にとっては、このやりとり自体が実践的な学びだった。「なぜこのバリデーションが必要なのか」「テンプレートリテラルの何が危険なのか」を、実際のコードを見ながら理解できた。教科書で読むより、自分のプロジェクトで脆弱性を見つける方がずっと身につく。

## Step 4：AIにAIのコードをレビューさせた

### 💬 プロンプト④

> コミットの前にソース修正のレビューを行ってください

### 🤖 AIのレビュー結果

変更された全モジュールを読み込んで、こんなレビューが返ってきた：

> セキュリティ対策（合格） — UUID検証の導入、フィルタ構築の修正は適切。脆弱性は解消。
>
> 型定義（妥協点あり） — 一部の型チェックが無効化されている。動作には影響しないが、将来的に改善すべき。
>
> 結論：コミットOK。

「型定義の技術的負債は将来のタスク」という判断が返ってきたのが印象的だった。

## Step 5：1行直して、42件のテストを自動生成

### 💬 プロンプト⑤

> GitHubへのプッシュでビルドエラーが発生しているので、エラー解消後にユニットテスト作成を行ってください

### 🤖 AIの対応

まずビルドエラーの原因を特定。React Nativeに存在しないWeb用のCSSプロパティが紛れ込んでいた。1行削除して解決。

そのあとすぐにテスト作成に移ってくれた。テストフレームワークのセットアップから、テストコード2ファイルまで一気に生成。

テストの内容はこんな感じ：

- XSS防止のサニタイズ処理が正しく動くか — 7件
- メールアドレスの正規化 — 2件
- パスワード強度の判定 — 6件
- エラーメッセージの汎用化（列挙攻撃防止） — 5件
- UUID検証でSQLインジェクション文字列を弾けるか — 10件
- その他パターンマッチ — 12件

実行結果：

```
Test Suites: 2 passed, 2 total
Tests:       42 passed, 42 total
Time:        2.996 s
```

42件全部グリーン。

42件のテストを手で書いたら半日はかかる。それが数分で生成された。これがAI開発の最大のメリットだと思う。

## Step 6：CI/CDで3回連続失敗して学んだこと

GitHubにコードをプッシュするたびに自動でテストが走る仕組み（CI/CD）を構築しようとした。最初から「プッシュ → テスト → iOSビルド → TestFlight」まで全自動を目指した。

結果、3回連続で失敗した。

### 💬 → 🤖 の流れ（3ラウンド）

1回目：「プロジェクトが初期化されてない」と怒られた → 初期化ステップを追加
2回目：「プロジェクトが存在しない」と怒られた → 強制作成フラグを追加
3回目：「証明書がない」と怒られた → …詰んだ

3回目のエラーで気づいた。Apple Developerの証明書がないと、iOSビルドはそもそもできない。

最終的に、AIがワークフローを根本的に再設計した：

```
【修正前】毎回のプッシュでiOSビルドまで実行（毎回失敗）
【修正後】毎回のプッシュではテスト42件だけ実行。iOSビルドは手動で
```

この修正でCIがグリーンになった。

教訓：最初から完璧を目指さない。まず動くものを作って、段階的に拡張する。CIも、アプリも、同じことだった。

## AIとの開発で、一番大事だと思ったこと

良かった点はたくさんある。コード生成の速さ、テスト作成の楽さ、セキュリティ監査の網羅性。

でも一番の気づきは、「AIが書いたコードには脆弱性がある」ということだった。

Step 1でAIが生成したコードに、Step 3でAI自身が脆弱性を見つけた。「生成」と「レビュー」は別の能力。人間も同じで、自分で書いたコードのバグに自分では気づけないことがある。

だからこそ、AIに対してもレビューを依頼する。セキュリティ監査を依頼する。テストを書かせて検証する。AIを使うほど、人間の判断力が問われる。

そして、新人エンジニアにとって、この開発プロセスそのものが最高の教材だった。AIが生成したコードを読み解く作業を通じて、TypeScriptの型システム、PostgreSQLのRLS、CIの仕組み、認証設計…業務では触れない領域まで一気に学べた。分からないところはその場でAIに質問すれば、コードの文脈を踏まえた回答が返ってくる。参考書を読むより、はるかに実践的だった。

AIは最高の相棒だけど、人間が手綱を握る必要がある。
